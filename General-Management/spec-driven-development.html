Spec-Driven Development

by Jag Singh, July 2026

Home : Spec-Driven Development

Spec-driven development makes a claim: stop putting your intent into the prompt of the moment and start putting it into a durable artifact that machines implement against. Instead of asking an AI to write code and improvising the intent conversationally, you author a spec and let agents generate, test, and revise the implementation until it conforms. The spec defines the outcomes, the constraints, and the acceptance criteria.

Spec is a layer in the fidelity stack

The system is a stack of layers of increasing fidelity. Each layer of the stack is a lossy compression of the one beneath it. The lossiness is not a defect, for example: a spec as detailed as the code would not be a spec, it would be a second copy of the code in a worse notation. The falsifiability line sits at the spec: above it, drift is caught by judgment; below it, by machines.

Each layer is the output of the layers above, a gate on the layers below, and knowledge feeding the context of every generation. The system exists in a world, and the context must carry the world's wisdom as well. The size of context is limited and fed intentionally: pinned means included unconditionally; queried means fetched exactly; retrieved means sampled by similarity.

The privileged layer fallacy

When a human changes the code and not the spec - and someone always will - the two diverge without ceremony. If the spec has teeth, the divergence surfaces immediately as a red check and forces a deliberate choice: fix the code or fix the spec. If it doesn't, the spec quietly becomes a description of a system that no longer exists, and the damage is deferred to the worst possible moment - typically when the next agent ingests the stale document as pinned truth and confidently reverts a correct change, or canonizes an incorrect one. An out-of-date spec is not neutral. It is an actively misleading instruction, delivered with full authority.

No layer on the stack has inherent authority, and change legitimately enters anywhere. A change in macro environment lands at the spec. A discovered bug lands at code. A capacity constraint lands near the bottom and propagates up. A methodology that insists every change originate at the spec forces teams to pretend, to backfill the document after the fact and call it the source. That pretense is precisely how specs rot into fiction: the words claim to lead while actually trailing. The real invariant is not that the spec leads. It is that no two adjacent layers are permitted to sit in contradiction: perturb any rung, and either its neighbors reconcile or a gate fires.

Choose a fixed point deliberately, and hold it per change, not forever. The stack supplies no natural center, which is exactly why declaring one is a governance act someone must consciously perform. The declaration should be a decision made in view of where the truth of a given change actually lives, not a doctrine that forbids reality from entering the stack anywhere else.

Detect drift in both directions. The forward gate catches code that violates the spec. The reverse check catches the other failure: a spec gone stale while the code moved on legitimately.

The resolution trap

The fidelity gaps between adjacent layers of the stack are not uniform, and the width of a gap determines its risk. Where two layers sit close in fidelity, translation between them is cheap and trustworthy - a compiler turning code into machine code invents almost nothing. Where the gap is wide, translation must invent, and invention is where the danger lives. The crossing from strategy to spec is wide; it is the classic product failure. The crossing from spec to code is wide, and it is exactly where the language model now sits: a non-deterministic translator filling large gaps with plausible judgment.

Because the spec is necessarily coarser than the code, everything below its resolution is left open deliberately. Two builds that both satisfy the criteria may differ in every line, and with a non-deterministic generator they will. This is correct behavior: the spec defines an equivalence class of acceptable implementations, and each build is a member. But the freedom bites in two specific ways. Anything you actually care about that varies between builds is something you under-specified. The variation audits your spec for you, painfully, by re-rolling the property you forgot to pin. And the shipped artifact stops being reproducible from the spec alone: you can regenerate a valid implementation, never the implementation you reviewed. For anything audited, that distinction is not academic.

Arm the spec, or don't bother writing it. Express intent as falsifiable acceptance criteria and wire them to tests that run on every change.

Freeze what ships. The spec guarantees the equivalence class; the audit attaches to a member. Generate, review, commit the specific artifact, and make regeneration a deliberate act with its own review - never a silent side effect of the pipeline.

Conclusion

A document named spec.md does not make a spec. A spec and a prompt are made of the same material: natural language stating intent; and nothing about the text distinguishes them. Versioning doesn't do it: a prompt in source control is a well-tracked wish. Review doesn't do it either: a merge gate approves changes to the words, but it never checks whether any output actually conformed to them. Structure doesn't do it: you can write a rigorously organized prompt and a sloppy stream-of-consciousness spec.

The only thing that converts a statement of intent into a spec is an enforcement mechanism: something that can reject the work for violating it, a test that goes red, a validation that fails the build. It is a spec only if something can fail against it, automatically, on every change. Else, it is just another prompt with ambitions, no matter what the filename says.
